## Project Requirements (from Navigator handoff)

Build a **best-in-class, browser-based Lego Builder web application** that allows users to:

- Interactively place, move, rotate, and remove virtual Lego bricks in a 3D scene
- Snap bricks to a grid/stud system that mirrors real Lego geometry
- Experience smooth, performant 3D rendering entirely in the browser (no plugin required)
- Enjoy intuitive UX patterns for 3D building tools (camera control, brick palette, undo/redo)
- Optionally share or export their creations

- Brick/block building mechanics and snap-to-grid systems
- Existing open-source Lego/brick-building references

## Technical Recommendations

### 1. 3D Rendering Engine: Three.js (Recommended)

**Rationale:**
- Largest community and ecosystem for browser 3D (100k+ GitHub stars)
- Mature, well-documented, actively maintained (r160+ as of 2026)
- Excellent performance with `InstancedMesh` for rendering thousands of identical bricks efficiently
- Rich plugin ecosystem: `OrbitControls`, `TransformControls`, `DragControls`, post-processing
- Lighter bundle than Babylon.js for a focused use case
- Most open-source Lego/voxel references use Three.js — lower ramp-up

**Babylon.js** is a strong alternative with a built-in physics engine and inspector, but its larger bundle size and steeper learning curve make it secondary for this use case.

**Raw WebGL** is ruled out — too low-level for a product-quality app.

### 2. Brick Geometry Strategy

**Option A — Procedural Geometry (Recommended for MVP):**
- Generate brick geometry programmatically using Three.js `BoxGeometry` + stud cylinders
- Parameterize by width (W), depth (D), height (H) in standard Lego units (1 stud = 8mm LDU)
- Supports 1x1, 1x2, 2x2, 2x4, plates, tiles, slopes as first-class types
- Fast to load, no external assets required

**Option B — LDraw Part Library:**
- Parse official `.dat` files from the LDraw parts library using `ldraw-three` or a custom parser
- Provides photorealistic, accurate geometry for 10,000+ official parts
- Higher complexity; recommended for v2 after MVP validation

### 3. Snap-to-Grid / Stud System

- Define a **world grid** in Lego units: 1 stud = 8 LDU on X/Z, 1 plate = 3.2 LDU on Y, 1 brick = 9.6 LDU on Y
- On brick placement, **raycast** from camera through mouse position onto the build plane or top face of existing bricks
- Snap the ghost/preview brick to the nearest valid stud position: `Math.round(pos / STUD_SIZE) * STUD_SIZE`
- Validate placement: check for collisions with existing bricks using an **occupancy grid** (3D sparse Map keyed by `x,y,z`)
- Highlight valid (green) vs. invalid (red) placement in real time using a ghost brick material

### 4. State Management & Undo/Redo

- Represent the build as an **immutable array of brick records**: `{ id, type, x, y, z, rotation, color }`
- Use a **command pattern** (or Redux-style reducer) for all mutations: `ADD_BRICK`, `REMOVE_BRICK`, `MOVE_BRICK`, `COLOR_BRICK`
- Maintain an undo stack (max 100 entries) and redo stack
- Serialize state to JSON for save/load and sharing

### 5. Camera & Controls

- **OrbitControls** (Three.js addon) for rotate/pan/zoom — industry standard for 3D builders
- Right-click drag = orbit; middle-click drag = pan; scroll = zoom
- Provide preset camera angles (top, front, side, isometric) via toolbar buttons
- Implement **camera collision** to prevent clipping into the build plate

### 6. UI/UX Patterns

| Pattern | Recommendation |
|---|---|
| **Brick palette** | Left sidebar with categorized brick types; search/filter; drag-to-place |
| **Color picker** | Palette of official Lego colors (BrickLink color list); apply to selected brick |
| **Tool modes** | Build mode, Select mode, Delete mode, Paint mode — toolbar toggle |
| **Ghost brick** | Semi-transparent preview brick follows cursor before placement |
| **Selection** | Click to select; Shift+click for multi-select; bounding box highlight |
| **Undo/Redo** | Ctrl+Z / Ctrl+Y; visible in toolbar with step count |
| **Grid toggle** | Show/hide base plate grid |
| **Minimap** | Optional top-down 2D minimap for large builds |
| **Export** | Download as JSON (native), LDraw .ldr (interop), PNG screenshot |

### 7. Performance Considerations

| Challenge | Solution |
|---|---|
| **Thousands of bricks** | `THREE.InstancedMesh` — render N identical bricks in 1 draw call |
| **Geometry complexity** | LOD (Level of Detail): simplified geometry at distance |
| **Raycasting cost** | Use `BVH` (three-mesh-bvh library) for fast intersection tests |
| **Memory** | Dispose unused geometries/materials; pool brick meshes by type |
| **Bundle size** | Tree-shake Three.js; lazy-load brick type modules |
| **Mobile** | Responsive layout; touch controls (pinch-zoom, two-finger pan) |

## Risks and Open Questions

### Risks

| Risk | Severity | Mitigation |
|---|---|---|
| **Performance degradation at scale** (1000+ bricks) | High | InstancedMesh + BVH raycasting from day 1; set a brick count limit for MVP |
| **Snap/collision logic complexity** | Medium | Define occupancy grid data structure early; write unit tests before 3D integration |
| **Mobile/touch UX** | Medium | Design touch controls in parallel with desktop; test on real devices early |
| **LDraw part geometry licensing** | Low-Medium | Use procedural geometry for MVP; evaluate LDraw license (CC BY 4.0) for v2 |
| **Bundle size bloat** | Medium | Audit with `vite-bundle-visualizer`; tree-shake aggressively |
| **Browser WebGL compatibility** | Low | Three.js handles fallbacks; target WebGL2 (97%+ browser support as of 2026) |
| **Undo/redo memory usage** | Low | Cap undo stack at 100 entries; use structural sharing via Immer |

### Open Questions for PM/Architecture

1. **Multiplayer / collaboration?** Real-time co-building would require WebSocket/CRDT layer — significant scope increase.
2. **User accounts & cloud save?** Determines backend requirements (auth, database, storage).
3. **Official Lego part library?** Legal review needed if using LDraw parts derived from official CAD data.
4. **Mobile-first or desktop-first?** Impacts control scheme and UI layout priorities.
5. **Brick count target for MVP?** Recommend capping at 500 bricks for MVP performance guarantee.
6. **Export formats beyond JSON?** LDraw (.ldr), OBJ, GLTF — each adds scope.
7. **Accessibility requirements?** 3D builders are inherently challenging for screen readers; define minimum a11y bar.

│   ├── <Scene />        — lighting, grid, environment

### Data Model

```typescript
interface Brick {
  id: string;           // UUID
  type: BrickType;      // '1x1' | '1x2' | '2x2' | '2x4' | 'plate-1x2' | ...
  position: [x: number, y: number, z: number];  // in LDU
  rotation: 0 | 90 | 180 | 270;  // Y-axis rotation in degrees
  color: LegoColor;     // from official Lego color palette
}

interface BuildState {
  bricks: Map<string, Brick>;
  occupancy: Map<string, string>;  // 'x,y,z' -> brick id
  selectedIds: Set<string>;
  history: BuildSnapshot[];        // undo stack
  future: BuildSnapshot[];         // redo stack
}
```
